# Test-design ядра СМП

## 1. Основание и правила

Объекты тест-дизайна:
- `POST /api/internal/authorize` (Authorization)
- API Card-Management

Условные идентификаторы требований:

| ID | Требование |
|---|---|
| AUTH-01 | Существующая карта получается из CMS, неизвестная карта отклоняется с кодом `14` |
| AUTH-02 | Только `ACTIVE` проходит дальше, `INACTIVE`, `BLOCKED`, `EXPIRED` отклоняются |
| AUTH-03 | Истекший `expiryDate` отклоняется с кодом `54`, текущий месяц еще действителен |
| AUTH-04 | `usedDaily + amount <= dailyLimit`, превышение дает `61` |
| AUTH-05 | `usedMonthly + amount <= monthlyLimit`, превышение дает `61` |
| AUTH-06 | `amount <= availableBalance`, превышение дает `51` |
| AUTH-07 | Успех дает `APPROVED/00`, одно резервирование, 12-значный RRN и 6-символьный authCode |
| AUTH-08 | Обязательные поля и их длины валидируются до бизнес-логики |
| CM-01 | `POST /api/cards` создает карту по зарегистрированному шестизначному BIN |
| CM-02 | PAN содержит 16 цифр, проходит Luhn и уникален, `expiryDate` имеет MMYY |
| CM-03 | `GET /api/cards/{pan}` возвращает существующую неудаленную карту, иначе 404 |
| CM-04 | `PATCH` частично обновляет допустимые статус, лимиты и баланс |
| CM-05 | `DELETE` выполняет soft delete, `DELETED` не выдается и не участвует в транзакциях |
| CM-06 | Генератор принимает `count >= 1`, непустой список корректных BIN и распределяет карты |
| CM-07 | Reserve принимает `amount > 0` и уникальный 12-значный RRN, уменьшает баланс один раз |
| CM-08 | Карточное событие публикуется через outbox, недоступность RabbitMQ приводит к retry, а не к потере карты |

Правила:

- сначала выполняется позитивный тест
- в негативном тесте изменяется только один класс
- денежные значения задаются в копейках
- `below/equal/above` относятся к **остатку** лимита (`limit - used`), а не к полному лимиту
- при несовпадении ТЗ и реализации ожидаемый результат задается по ТЗ, а расхождение оформляется как дефект

## Попарное тестирование

### 5.1 Модели и ограничения

- Authorization: 7 параметров, 864 допустимые комбинации после ограничений. Неактивная карта не комбинируется с превышением денег, а истекший срок - с недостаточным балансом, потому что алгоритм завершится раньше.
- Card-Management: 7 параметров, 160 допустимых комбинаций. Ограничения обеспечивают один невалидный класс на негативный тест. `outbox=unavailable` используется только для запроса, прошедшего валидацию и разрешение BIN. Сочетание нулевого дневного лимита с месячным лимитом ниже дневного исключено как численно невозможное при неотрицательных лимитах.
- Полный перебор до ограничений: Authorization `4×3×3×3×3×3×4=3888`, Card-Management `3×3×3×3×4×3×2=1944`.
- Официальный `pict.exe` сгенерировал 25 и 26 строк соответственно. Его статистика: Authorization - 206 combinations, Card-Management - 153 combinations. Независимая проверка подтвердила покрытие 206/206 и 153/153 допустимых пар, непокрытых пар 0.

Файлы: `pict/model.txt`, `pict/cases.txt`, `pict/model-card-management.txt`, `pict/cases-card-management.txt`. Первая строка каждого `cases*.txt` - заголовок, поэтому номер source row ниже совпадает с номером строки данных, а не с физической строкой файла.

Если несколько условий отказа сочетаются, ожидается первое по порядку AUTH-02 → AUTH-03 → AUTH-04 → AUTH-05 → AUTH-06.

### 5.3 Общий шаблон Card-Management pairwise

**P-CM:** Card-Management и PostgreSQL healthy. Для `registered_valid` BIN существует в справочнике, для `unregistered_valid` - отсутствует. Запрос имеет уникальный correlation key. Используются значения `positive=100000`, `zero=0`, `negative=-1`. Monthly относительно daily задается `daily+1`, `daily` или `daily-1`. Последний вариант разрешен только при положительном daily limit.

**S-CM:** собрать тело по строке `cases-card-management.txt`, выполнить `POST /api/cards`, проверить HTTP/схему, наличие ровно одной новой карты, 16-значный Luhn-valid PAN, expiry=current+3 years и запись outbox. Критичные сочетания сверх pairwise:

- повтор одного RRN при параллельном reserve
- два параллельных reserve на остаток, достаточный только для одного
- массовая генерация при коллизии PAN
- восстановление RabbitMQ после накопления нескольких outbox-событий

Они не заменяют pairwise и выполняются как отдельные интеграционные тесты.

## 6. Критерий покрытия

- Каждый класс в разделах 2.1-2.2 имеет хотя бы одного представителя в целевом, BVA или pairwise-кейсе.
- Каждая числовая/структурная граница проверяется точками ниже, ON и выше, если значение существует в домене.
- Каждая строка обоих pairwise-наборов имеет отдельный ID `PW-A-*` или `PW-C-*` и ожидаемый результат.
- В негативных Card-Management pairwise-кейсах присутствует ровно один невалидный класс.
- Успех проверяется по ответу и побочным эффектам. Отказ проверяется по ответу и отсутствию побочных эффектов.
